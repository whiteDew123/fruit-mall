# 数据库设计（表字典与状态枚举）

> 本文档是数据库结构的**唯一来源**：表结构、字段、索引、枚举取值的解释以本文为准，
> 机器可执行的建表语句以 `fruit-mall/deploy/sql/01_schema.sql` 为准，两者必须一一对应。
> 版本：v1.0（2026-09-27）。变更规则见第 9 节。

---

## 1. 通用约定

| 项 | 约定 |
|---|---|
| 数据库名 | `fruit_mall` |
| 字符集 / 排序规则 | `utf8mb4` / `utf8mb4_general_ci` |
| 存储引擎 | InnoDB |
| 业务表前缀 | `fm_`；系统权限与日志表前缀 `sys_` |
| 表名风格 | 小写下划线，尽量用单数（`fm_product_spu`）。例外：`fm_orders`、`fm_order_item`、`fm_order_status_log` 用复数/复合名，原因是 `order` 是 MySQL 保留字，写成 `fm_order` 后每处都必须加反引号，漏写即语法错误，风险高于命名一致性收益 |
| 主键 | `id`，`BIGINT NOT NULL AUTO_INCREMENT` |
| 公共字段 | `create_time`、`update_time`、`create_by`、`update_by`、`deleted`，由 `MetaObjectHandler` 自动填充，业务代码不手工赋值 |
| 逻辑删除 | `deleted`：0 未删除 / 1 已删除，由 `@TableLogic` 接管，业务 SQL 不写 `deleted = 0` |
| 时间 | `DATETIME`，格式 `yyyy-MM-dd HH:mm:ss`；仅日期用 `DATE` |
| 金额 | `DECIMAL(10,2)`，Java 侧 `BigDecimal`，禁止 `double` / `float` |
| 比例/评分 | `DECIMAL(8,6)`（推荐得分）或 `TINYINT`（1–5 星级） |
| 外键 | **不建数据库外键约束**，一致性由 Service 层与 `check_consistency.sql` 保证，便于造数据与迁移 |
| 状态字段 | 统一命名 `status`（或语义化字段名如 `behavior`、`node`、`type`），取值只定义在本文第 3 节与 `com.fruitmall.common.enums`，代码中禁止散落状态字面量 |
| 布尔语义 | 用 `TINYINT`，0 否 / 1 是 |
| 约束 | 关键数值列加 `CHECK`（库存、金额、星级），由数据库兜底拦截负值与越界值 |

### 1.1 公共字段的例外

| 表 | 例外 | 原因 |
|---|---|---|
| `sys_user_role`、`sys_role_menu` | 用物理删除，不含 `deleted`、`update_time` | 重新授权时按"先删后插"处理，保留逻辑删除会与唯一索引冲突并留下垃圾行 |
| `sys_oper_log`、`sys_login_log` | 只追加不修改，不含 `update_time`、`update_by`、`deleted` | 日志表不做逻辑删除，归档由定期清理脚本负责 |
| `fm_user_behavior`、`fm_recommend_trace` | 只追加不修改，审计字段只保留 `create_time` | 行为埋点与推荐留痕是"事实记录"，不允许被业务改写 |

| `category`、`product_spu`、`product_sku`、`product_attr_def`、`product_attr_value`、`product_image`、`product_feature` | `fm_category`、`fm_product_spu`、`fm_product_sku`、`fm_product_attr_def`、`fm_product_attr_value`、`fm_product_image`、`fm_product_feature` |
| `inventory_batch`、`inventory_transaction` | `fm_inventory_batch`、`fm_inventory_transaction` |
| `cart_item`、`orders`、`order_item`、`order_status_log`、`payment_record`、`refund_record` | `fm_cart_item`、`fm_orders`、`fm_order_item`、`fm_order_status_log`、`fm_payment_record`、`fm_refund_record` |
| `fulfillment_order`、`fulfillment_trace` | `fm_fulfillment_order`、`fm_fulfillment_trace` |
| `after_sale`、`after_sale_item`、`review`、`review_tag` | `fm_after_sale`、`fm_after_sale_item`、`fm_review`、`fm_review_tag` |
| `recommend_config`、`recommend_trace`、`recommend_feedback` | `fm_recommend_config`、`fm_recommend_trace`、`fm_recommend_feedback` |

本版**不建**的四张表及原因：

| 未建表 | 原因 |
|---|---|
| `cart`（购物车主表） | 购物车只按会员维度存条目，不需要主表；`fm_cart_item` 直接挂 `member_id` 更简单，减少一次关联查询 |
| `recommend_result_cache` | 结果缓存由 Redis 承担，落库冗余；需要追溯时用 `fm_recommend_trace` |
| `stat_daily_sales`（汇总表） | 第一版经营分析直接对订单表聚合（数据量 300 单级别），汇总表在性能需要时再补 |
| `fm_product_feature`（商品特征向量） | 500 会员 × 200 SPU 的规模下，特征向量内存计算是毫秒级，Redis 缓存已足够；落库只换来"重启免重算"，却要多一套"属性变更触发重算"的同步逻辑和一处潜在不一致。推荐模块上线后若确有必要再补，届时按第 9 节的变更规则先改本文档与脚本 |

### 2.1 落地阶段（代码读写范围与论文口径必须一致）

34 张表全部建好，但**不是每张都会在第一时间被代码读写**。下表把节奏说清楚，避免出现"论文里写了、系统里没有"的缺口，
也避免答辩时被问"这张表用到了吗"答不上来。本期指 10 月 7 日前的冲刺版本。

| 表 | 阶段 | 依据 |
|---|---|---|
| `fm_inventory_transaction` | 本期 | 下单、支付、取消都要写流水，是库存一致性的证据 |
| `fm_inventory_batch` | 第二阶段 | 本版先做 SKU 单层条件更新扣减；批次 FIFO、临期预警按 `docs/03-开发计划.md` 的 P1 清单顺延，字段已按完整设计建好，避免后期改表 |
| `fm_recommend_trace` | 本期 | 推荐理由与各因素得分留痕，是"可解释"与实验数据的来源 |
| `fm_recommend_config` | 第二阶段 | 本版权重走配置文件；后台可视化编辑页顺延，配置表先建好 |
| `fm_recommend_feedback` | 第二阶段 | "不感兴趣"属偏好管理，标为 P1；行为日志先用 `fm_user_behavior` 的 `DISLIKE` 记录 |
| `fm_refund_record` | 第二阶段 | 本版售后只做"申请 + 审核 + 状态展示"，退款确认顺延 |
| 其余 28 张 | 本期 | 覆盖商品、库存、交易、履约、售后、评价、权限的完整闭环 |

**维护要求**：某个第二阶段功能提前落地时，把本表对应行的"阶段"改为"本期"；功能被砍掉时，要么删表，要么在此明确写为扩展设计。

### 3.7 四个状态机的迁移规则

**订单**

| 当前 | 允许迁移到 | 触发者 | 前置校验 |
|---|---|---|---|
| 待支付 10 | 已支付 20 / 已取消 60 | 支付回调 / 用户、系统超时 | 支付成功且金额一致 / 超过 30 分钟 |
| 已支付 20 | 备货中 30 / 退款中 70 | 履约人员 / 售后审核通过 | 履约单创建成功 / 仅退款审核通过 |
| 备货中 30 | 配送中 40 | 履约人员 | 分拣完成且库存实扣成功 |
| 配送中 40 | 已完成 50 | 履约人员、用户确认 | 送达并签收 |
| 已完成 50 | 退款中 70 | 售后审核通过 | 退货退款场景 |
| 退款中 70 | 已退款 80 | 系统 | 退款成功 |
| 已取消 60 / 已退款 80 | 终态 | — | — |

**支付**：`INIT 10 → PAYING 20 → SUCCESS 30 / FAILED 40`；`INIT|PAYING → CLOSED 50`（取消或超时）；`SUCCESS 30 → REFUNDING 60 → REFUNDED 70`。

**履约**：`待分拣 10 → 分拣完成 20 → 待配送 30 → 配送中 40 → 已送达 50 → 已签收 60`，不得跳级；非终态可转 `异常 90`，异常修复后回到当前正常节点。

**售后**：`待审核 10 → 已同意 20 / 已驳回 30 / 已取消 70`；`已同意 20 → 退款中 50`（仅退款）或 `→ 退货中 40`（退货退款）；`退货中 40 → 退款中 50`（收到退货）；`退款中 50 → 已完成 60`；`已驳回 30 / 已完成 60 / 已取消 70` 为终态。

非法迁移一律抛 `BizException`（HTTP 409）并记入日志，例如"待支付 → 配送中"、"已取消 → 已支付"。

## 4. 表字典

每张表都包含第 1 节的公共字段（除 1.1 列出的例外），下表只列业务字段。

### 4.1 系统权限

**`sys_user` 系统用户**

| 字段 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|
| `username` | VARCHAR(50) | 否 | — | 登录名，唯一 |
| `password` | VARCHAR(100) | 否 | — | BCrypt 密文（60 字符） |
| `nickname` | VARCHAR(50) | 否 | — | 显示名 |
| `real_name` | VARCHAR(50) | 是 | NULL | 真实姓名 |
| `phone` | VARCHAR(20) | 是 | NULL | 手机号（列表页脱敏） |
| `email` | VARCHAR(100) | 是 | NULL | 邮箱 |
| `avatar` | VARCHAR(255) | 是 | NULL | 头像地址 |
| `status` | TINYINT | 否 | 10 | 见 `SysUserStatusEnum` |
| `last_login_time` | DATETIME | 是 | NULL | 最后登录时间 |
| `remark` | VARCHAR(255) | 是 | NULL | 备注 |

## 5. 索引设计要点

| 场景 | 索引 | 说明 |
|---|---|---|
| 超时关单扫描 | `fm_orders(status, expire_time)` | 定时任务只扫 `status = 10 AND expire_time < now()` |
| 会员订单列表 | `fm_orders(member_id, status)` | 覆盖"我的订单"按状态筛选 |
| 行为画像聚合 | `fm_user_behavior(member_id, create_time)` | 按会员取时间窗行为 |
| 商品热度统计 | `fm_user_behavior(target_id, behavior, create_time)` | 近 7 天销量/加购量 |
| 库存对账 | `fm_inventory_transaction(sku_id, create_time)` | 流水累加与当前库存比较 |
| 幂等兜底 | `fm_orders.order_no`、`fm_payment_record.pay_no`、`fm_refund_record.refund_no`、`fm_inventory_batch.batch_no` | 业务唯一键，重复提交由数据库拦截 |
| 一次性约束 | `fm_review(order_item_id)`、`fm_fulfillment_order(order_id)`、`fm_payment_record(order_id)` | 一对一关系的唯一性保证 |
| 防重复反馈 | `fm_recommend_feedback(member_id, spu_id)` | 同一会员对同一商品只保留一条反馈 |

## 6. 一致性约束与技术手段的对应

| 编号 | 规则 | 落地手段 |
|---|---|---|
| R-01 | 上架必须有图、价格 > 0、必填属性齐全、库存 > 0 | Service 校验 + `fm_product_sku.price > 0` CHECK + `fm_product_attr_def.required` |
| R-02 | 加购需商品上架、库存 > 0、不超限购 | Service 校验 + `uk_member_sku` 合并同一 SKU |
| R-03 | 下单重新校验价格与库存、锁定库存、生快照 | Service + 事务 + `fm_product_sku` 条件更新 + `fm_order_item.sku_snapshot` |
| R-04 | 支付幂等、金额一致、订单需待支付 | `uk_pay_no` + `uk_order_id` + 状态机守卫 + 金额比对 |
| R-05 | 30 分钟超时关单并释放库存 | `idx_status_expire` 定时任务 + 状态机 + 库存流水 |
| R-06 | 仅待支付/已支付可取消 | 状态机守卫 + 409 |
| R-07 | 履约不得跳级 | 履约状态机 + `fm_fulfillment_trace` 留痕 |
| R-08 | 可售后数量 ≤ 订单项数量 − 已售后数量 | `fm_order_item.after_sale_quantity` + CHECK + Service 校验 |
| R-09 | 退货回补进"退货暂存"批次，不回可售库存 | `fm_after_sale_item.return_batch_id` + 批次状态 40 + 流水类型 50 |
| R-10 | 仅已完成订单可评价，一订单项一次 | `uk_order_item` + `fm_order_item.reviewed` + 状态校验 |
| R-11 | 并发不超卖、不出现负库存 | 条件更新 `WHERE stock - locked_stock >= ?` + `stock >= 0` CHECK + JMeter 并发验证 |
| R-12 | 下架商品下单拦截 | Service 校验 + 购物车项置为失效（状态 20） |

## 8. 四个状态机的代码落点

| 状态机 | 类 | 允许的迁移方法 |
|---|---|---|
| 订单 | `OrderStateMachine` | `pay`、`startPicking`、`deliver`、`complete`、`cancel`、`refund` |
| 支付 | `PaymentStateMachine` | `paying`、`success`、`fail`、`close`、`refund` |
| 履约 | `FulfillmentStateMachine` | `pick`、`pack`、`deliver`、`arrive`、`sign`、`exception` |
| 售后 | `AfterSaleStateMachine` | `approve`、`reject`、`return`、`refund`、`complete`、`cancel` |

统一对外暴露 `transition(业务号, 目标动作)`，内部校验当前状态是否允许该动作，不允许则抛 `BizException`（409）。
**状态字段只能被状态机修改**，Mapper 中不出现裸的 `update ... set status = ...`。

## 9. 变更规则

1. 任何表结构变更，**先改本文档，再改 `deploy/sql/01_schema.sql`，最后改代码**；顺序颠倒视为违规。
2. 新增枚举取值必须同时更新本文第 3 节与 `com.fruitmall.common.enums` 中的枚举类，两处取值必须一致。
3. 已上线的表不做破坏性变更（删列、改类型）；需要时新增列并保留旧列一个版本。
4. 禁止手工改库不入脚本；开发期的结构试验也必须落到脚本里再执行。
