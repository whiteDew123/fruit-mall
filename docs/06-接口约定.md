# 接口约定

> 本文档只写**接口清单、错误码与跨接口的通用约定**；具体参数与响应结构由 Knife4j 自动生成，
> 不手写、不重复维护（启动后端后访问 `http://localhost:8080/doc.html`）。
> 版本：v0.1（2026-09-28）。

---

## 1. 通用约定

| 项 | 约定 |
|---|---|
| 消费者端前缀 | `/api/shop/{模块}/{资源}` |
| 商家后台前缀 | `/api/admin/{模块}/{资源}` |
| 登录注册 | `/api/auth/**` |
| 统一响应 | `{ code, message, data }`，`code` 与 HTTP 状态码一致 |
| 分页请求 | `pageNum`（从 1 开始）、`pageSize`（默认 10、上限 100） |
| 分页响应 | `data` 为 `{ pageNum, pageSize, total, list }` |
| 时间格式 | `yyyy-MM-dd HH:mm:ss`（由 `JacksonConfig` 统一处理 Java 8 时间类型） |
| 金额 | `BigDecimal` / `DECIMAL(10,2)`，禁止 double、float |
| 鉴权 | 请求头 `Authorization: Bearer <token>`；白名单接口除外 |
| 权限 | 后台接口方法上标注 `@RequiresPermission("{模块}:{操作}")` |
| 操作日志 | 后台**写操作**必须标注 `@OperLog(module = "...", action = "...")` |
| 幂等 | 下单、支付回调、退款确认必须幂等，业务唯一键加唯一索引兜底 |
| 文档 | Knife4j 自动生成，方法上补 `@Operation` 说明即可 |

### 1.1 免登录白名单

白名单集中在 `application.yml` 的 `fruit-mall.auth.exclude-paths` 维护，逗号分隔，**只改配置不改代码**。
当前内容：

```
/api/auth/admin/login,
/api/auth/member/login,
/api/auth/member/register,
/api/shop/category/**,
/api/shop/product/**,
/api/shop/behavior/report,
/api/files/**
```

后续首页推荐、相似推荐等公开接口在此追加。**上传目录 `/api/files/**` 必须保持公开**，
否则前端无法加载商品图片。

## 2. 错误码

`code` 与 HTTP 状态码一致，业务细分原因写在 `message` 中，前端可直接展示。

| code | 含义 | 典型场景 |
|---|---|---|
| 200 | 成功 | — |
| 400 | 参数校验失败 | DTO 校验不通过、登录名或密码错误、请求体格式错误 |
| 401 | 未登录或令牌失效 | 未携带令牌、令牌过期、令牌被篡改 |
| 403 | 无权限 | 角色缺少权限标识、账号被禁用、越权访问他人数据 |
| 404 | 资源不存在 | 接口路径不存在、商品或订单编号不存在 |
| 409 | 状态冲突 | 非法状态流转、库存不足、商品已下架 |
| 500 | 系统异常 | 未预期异常，堆栈只进日志不返回前端 |

### 3.2 数据归属校验约定

消费者端的会员、地址、购物车、订单等接口，一律在 Service 层用 `UserContext.getRequiredMemberId()` 取当前会员ID，
并在查询与更新时带上 `member_id` 条件。**后台账号调用消费者端接口返回 403**（用户类型不匹配），
**会员访问他人数据返回 404**（当作不存在处理，不泄露数据是否存在）。这两条已在会员、地址、购物车模块实测通过。

### 3.3 查询参数必须 URL 编码

`?reason=不想要了` 这种**未编码的非 ASCII 查询参数会被 Tomcat 在连接器层直接拒绝并返回 400**，
且该响应体是容器默认页面、不是统一响应格式。前端使用 axios 时其 `params` 会自动编码，正常不受影响；
手工用 curl / Postman 调试时必须编码，例如 `?reason=%E4%B8%8D%E6%83%B3%E8%A6%81%E4%BA%86`。

### 3.4 库存预占与释放口径

下单走"预占"而不是直接扣减，字段变化如下（`stock` 为可售量、`locked_stock` 为预占量）：

| 节点 | stock | locked_stock | 库存流水 |
|---|---|---|---|
| 下单成功 | −数量 | +数量 | 类型 20 预占，数量为负 |
| 支付成功（下一阶段实现） | 不变 | −数量 | 类型 40 实扣，数量为零变动、仅核销预占 |
| 取消 / 超时关单 | +数量 | −数量 | 类型 30 释放，数量为正 |

扣减语句必须与判断同处一条 SQL：
`UPDATE fm_product_sku SET stock = stock - ? , locked_stock = locked_stock + ? WHERE id = ? AND deleted = 0 AND status = 10 AND stock - locked_stock >= ?`，
**影响行数为 0 即库存不足，调用方必须整单回滚**。

### 3.5 支付幂等与一致性口径

本课题不接真实支付渠道，由前端在支付页选择模拟结果（成功 / 失败 / 超时），后端据此走不同分支，用于演示支付闭环与异常分支。

| 规则 | 落地方式 |
|---|---|
| 一个订单只有一条支付记录 | `fm_payment_record` 的唯一索引 `uk_order_id`；支付失败后复用同一条记录重新发起，不产生新的支付流水号 |
| 回调幂等 | `pay_no` 唯一索引；订单已支付成功时重复请求直接返回成功，**不重复核销库存、不新增库存流水** |
| 金额一致 | 支付前比对支付单金额与订单应付金额，不一致返回 409 并阻断 |
| 状态守卫 | 只有待支付订单可支付，必须经过 `OrderStateMachine`；已取消、已关闭、已支付订单支付一律 409 |
| 超时关单 | 定时任务每 60 秒扫描 `status = 10 且 expire_time < now()` 的订单；支付接口发现订单已超时也会立即关单 |

**支付成功时库存口径**：可售库存 `stock` 不变，只核销预占 `locked_stock`，
并累加 SKU 销量；库存流水记录一条类型 40（实扣）、变动数量为 0 的记录，备注中说明"核销预占"。
这样"流水累加 = 当前库存"的对账口径依然成立。

### 3.6 履约与订单状态的联动

履约推进与订单状态在同一事务内联动，任一步校验失败整体回滚，不会出现"履约走了、订单没动"的中间状态：

| 履约动作 | 履约状态 | 订单状态 |
|---|---|---|
| 支付成功（自动） | 生成履约单，待分拣 10 | 已支付 20 |
| 分拣完成 | 分拣完成 20 | 备货中 30 |
| 打包待配送 | 待配送 30 | 不变 |
| 出库配送 | 配送中 40 | 配送中 40 |
| 确认送达 | 已送达 50 | 不变 |
| 确认签收 | 已签收 60 | 已完成 50（写完成时间） |
| 异常登记 | 异常 90 | 不变，由人工介入处理 |

履约**不得跳级**：分拣完成后直接签收会被 `FulfillmentStateMachine` 拦截并返回 409。

### 3.7 评价规则

- 只有**已完成**订单可以评价，未完成订单提交返回 409；
- 一个订单项只能评价一次，由唯一索引 `uk_order_item` 与 `fm_order_item.reviewed` 双重保证；
- 匿名评价在列表中统一显示为"匿名用户"，不泄露会员身份；
- 被隐藏的评价不再出现在消费者端列表，但后台仍可查询与恢复。

### 3.8 售后流程与数量口径

**两种售后类型的流转路径**

| 类型 | 路径 |
|---|---|
| 仅退款 10 | 待审核 10 → 已同意 20 → 退款中 50 → 已完成 60 |
| 退货退款 20 | 待审核 10 → 已同意 20 → 退货中 40 →（商家收货）→ 退款中 50 → 已完成 60 |
| 异常分支 | 待审核 → 已驳回 30；待审核 → 已取消 70（会员撤销） |

**数量口径（R-08）**：申请时校验 `可售后数量 = 订单项数量 − 已售后数量`，校验通过后立即占用
`fm_order_item.after_sale_quantity`；驳回或会员撤销时归还。这样同一订单项的多次申请总量不会超过购买量。

**退货回补口径（R-09）**：生鲜退货不可二次销售，确认收到退货时只写入类型 50（退货回补）的库存流水，
**可售库存 `stock` 保持不变**，备注中注明"退货回补至退货暂存，不进入可售库存"。
退货暂存批次在批次库存阶段落地（`fm_after_sale_item.return_batch_id` 已预留字段）。

**订单与支付单联动**：审核通过时订单转入退款中 70、支付单转入退款中 60；确认退款完成时订单转入已退款 80、支付单转入已退款 70。
支付状态机不允许从"支付成功"直接跳到"已退款"，必须先经"退款中"，服务层对此做了兜底处理。

**适用范围**：本版仅"已支付"与"已完成"的订单可申请售后；备货中与配送中的订单会返回 409，
提示先完成收货或联系客服，避免与履约流程冲突。

**已知简化**：因退款关闭的订单，其履约单会停留在当时的状态（本版未定义履约单的终止状态），
留待库存批次与履约增强阶段一并处理。

### 3.1 操作日志的落库范围

`@OperLog` 切面只记录**业务方法真正执行**的后台写操作。以下情况不产生操作日志：

- 未登录（401）与权限不足（403）：请求在 `AuthInterceptor` 阶段就被拦下，业务方法未执行；
- 参数校验失败（400）：请求在进入方法前被 Spring Validation 拦下。

因此操作日志反映的是"实际执行的写操作"，包含成功与**执行中失败**两种结果（`result_status` 10 / 20），
失败时 `error_msg` 记录异常原因。若后续需要把 401/403 也纳入安全审计，可在全局异常处理中补充记录。
