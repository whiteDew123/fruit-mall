# 推荐算法实现方案（纯 Java，不需要 Python 服务）

> 回答：推荐算法是否必须用 Python？没有 Python 基础能不能做？具体实现流程是什么？

---

## 一、结论：不需要 Python

本课题选定的算法是**基于内容的多因素加权 + 物品协同过滤（ItemCF）**，本质是向量运算、矩阵统计和加权求和——**这些是数学，不是语言特性**。Java 全部能做，而且不需要引入任何机器学习库。

### 1.1 进一步说明：为什么很多人以为要用 Python

| 常见误解 | 事实 |
|---|---|
| "推荐算法必须用 Python" | 只有深度学习模型（PyTorch/TensorFlow）才基本锁定 Python。本课题不涉及神经网络 |
| "没有 pandas/sklearn 做不了特征工程" | 你的数据量是 200 商品 × 500 用户级别，Java 的 `List` / `Map` / `double[]` 完全够用，而且更快 |
| "Java 做不了实验评估" | 写一个带 `main` 方法的评估类，跑完输出 CSV，用 Excel 画图，与 Python 结果等价 |
| "不用 Python 答辩会扣分" | 算法得分看**模型设计是否合理、实验是否有对比、结论是否可信**，与实现语言无关。Java 实现反而少了"跨语言部署"这个扣分点 |

### 1.2 什么时候才真的需要 Python

只有三种情况：① 导师明确要求使用机器学习框架；② 你想做深度学习推荐（如 DeepFM、NeuralCF）；③ 你想用现成库快速跑很多对比模型。**三者都不是本课题的必要条件。** 如果后期想加，可以单独写一个 100 行左右的脚本做对比实验，不影响主系统。

### 1.3 用 Java 实现的额外收益

- 少部署一个 Python 服务，Docker Compose 少一个容器，答辩现场少一个出错点；
- 推荐逻辑与业务在同一个工程里，可以直接读数据库、直接调用商品服务，不用设计跨进程接口；
- 论文第 5 章"模块设计"可以把推荐类图、加权公式、伪码放在同一个技术体系里讲，逻辑更连贯。

## 二、数据量级判断（先消除心理压力）

假设规模：500 名会员 × 200 个 SPU（约 600 个 SKU）× 5 万条行为日志。

| 计算任务 | 复杂度 | 实际耗时（Java 内存计算） |
|---|---|---|
| 商品相似度矩阵（SPU×SPU） | 200×200 = 4 万个相似度 | 毫秒级 |
| 单个用户推荐（召回 + 打分） | 约 200 个候选 × 7 个因素 | 毫秒级 |
| 全量用户离线预计算 | 500 用户 × 200 候选 | 1 秒以内 |

**结论：不需要 Redis 之外任何中间件，不需要 Spark/Hadoop/向量数据库。** 特征可全量放入内存，用 `ConcurrentHashMap` 缓存即可，召回与排序在单机毫秒级完成。把这一点写进论文，是很好的工程判断力体现。

## 三、整体实现流程（十步）

```
① 埋点采集行为  →  ② 构建商品特征  →  ③ 构建用户画像  →  ④ 多通道召回
                                                                   ↓
⑩ 离线评估/实验  ←  ⑨ 降级与缓存  ←  ⑧ 理由生成与留痕  ←  ⑤ 过滤  ←  ⑥ 加权打分  ←  ⑦ 排序与打散
```

### ① 埋点采集行为

前端在浏览详情、搜索、加购、下单、评价、点"不感兴趣"时调用埋点接口，写入 `user_behavior_log`（行为类型、目标商品、来源场景、时间、会话 ID）。未登录用户用匿名 ID 记录，登录后合并。

这是**整个推荐系统的地基**，没有行为数据就没有个性化。建议在开发第一天就把这张表和埋点接口做出来，后面的每一步都在往里面攒数据。

### ② 构建商品特征向量（离线 + 缓存）

从 `product_attr_value`（特色属性表）读取结构化属性，转成定长数值向量并归一化到 `[0,1]`：

```
向量维度 = [甜度, 酸度, 脆度, 多汁度, 香气, 价格归一值, 规格归一值,
            产地纬度带, 糖度(Brix)归一值, 品级, 认证加分,
            当季标记, 临近季节标记, 保质期长度, 场景标签…]
```

落库到 `product_feature(spu_id, vector_json, price_norm, season_months, update_time)`，并在内存中缓存。**商品建档或属性修改时触发重算**（在 Service 里调用 `featureService.rebuild(spuId)`）。

### ③ 构建用户画像（离线定时任务）

从行为日志聚合出隐式偏好，公式为"行为权重 × 时间衰减"的加权平均：

```
偏好维度 d 的值 = Σ ( weight(行为) × exp(-λ × 距今天数) × 该商品在维度 d 上的值 ) / Σ ( weight × exp(...) )
```

行为权重：浏览 1.0、搜索点击 1.5、收藏 2.5、加购 3.0、下单 5.0、好评 4.0、差评 −4.0、退款 −5.0；半衰期取 14 天（`λ = ln2 / 14`）。

同时保留用户的显式偏好（口味问卷、忌口、价格区间）。定时任务建议每 30 分钟增量更新一次，登录用户访问首页时也可触发一次轻量更新。

### ④ 多通道召回（候选池 100–200）

| 通道 | 数据来源 | 输出 |
|---|---|---|
| R1 内容相似 | 用户偏好向量 × 商品特征向量余弦相似度 | Top 50 |
| R2 时令匹配 | `season_months` 命中当前月份，且属于用户历史偏好品类 | Top 30 |
| R3 热销榜单 | 近 7 天销量/加购量统计（分品类） | Top 30 |
| R4 ItemCF | 商品共现矩阵（同一订单/同一会话共现） | Top 50 |
| R5 库存协同 | 临期（剩余保质期 < 阈值）或滞销（30 天销量 < 阈值）且库存 > 0 | Top 20 |
| R6 兜底 | 新品保量、全站热销 | Top 20 |

各通道输出商品 ID 列表，`LinkedHashSet` 合并去重，保留"被多个通道召回"的信息（命中通道数可作为加分因子）。

### ⑤ 过滤

- 硬过滤：下架商品、库存为 0、命中用户忌口/过敏清单。
- 软处理：短期内已购买且未到"预计吃完周期"的商品**降权而非删除**（水果是消耗品，复购是常态）。

### ⑥ 多因素加权打分

```
score(u, i) = Σ_k ( w_k × f_k(u, i) ) / Σ_k w_k  − penalty(u, i)
```

| 因素 | 含义 | 默认权重 |
|---|---|---|
| f1 内容偏好匹配 | 用户画像与商品特征余弦相似度 | 0.25 |
| f2 时令匹配 | 当季 1.0 / 临近 0.5 / 反季 0.1 | 0.15 |
| f3 ItemCF 协同得分 | 与用户历史商品的相似度之和 | 0.15 |
| f4 热度 | 近 7 天销量归一值 | 0.15 |
| f5 价格匹配 | 与用户价格偏好中心的接近程度 | 0.10 |
| f6 品质与新鲜度 | 品级、糖度、认证、到货天数 | 0.10 |
| f7 库存协同压力 | 临期/滞销压力（商家可开关） | 0.10 |

惩罚项：`w_repeat × 复购惩罚 + w_dislike × 不感兴趣惩罚 + w_bad × 差评品类惩罚`。

**关键实现细节**：某一因素数据缺失时（新用户没有协同数据、新商品没有销量），该维度 `return null`，权重**不参与分母**，剩余维度自动重新归一化。这样新用户和新商品不会被"0 分"误伤——这是论文里值得专门写一段的设计。

### ⑦ 排序与多样性打散

按分数倒序取前 50，再用贪心 MMR 思路打散：逐个挑选时对"与已选商品同品类"的候选施加折扣，保证最终 Top 10 至少覆盖 3 个品类。这一步直接提升"覆盖率"和"长尾曝光占比"两项实验指标。

### ⑧ 理由生成与留痕

取贡献值最大的 1–2 个因素，套模板生成中文理由，连同每个因素的原始分、权重、贡献值一起写入 `recommend_trace`：

```json
{
  "memberId": 1001, "spuId": 88, "score": 0.83,
  "factors": [
    {"code": "SEASON", "value": 1.0, "weight": 0.15, "contribution": 0.15, "text": "当季上市"},
    {"code": "CONTENT", "value": 0.91, "weight": 0.25, "contribution": 0.2275, "text": "口味匹配：近90天6次购买高甜度芒果"}
  ],
  "reasonText": "当季上市；口味匹配：你近 90 天多次购买高甜度芒果",
  "configVersion": "v2026-10-05", "scene": "HOME"
}
```

这张表是"**展示推荐依据**"和"**算法可验证**"两项要求的落地，也是论文实验章节的数据来源。

### ⑨ 缓存与降级

- 缓存：`Redis key = recommend:{scene}:{memberId}:{configVersion}`，TTL 10 分钟；权重配置版本变化后 key 自然失效。
- 降级：推荐计算异常或超时（>3 秒）时，立即返回"热销 + 时令"规则排序结果并记录告警日志，前台不报错。**这个降级逻辑本身就是论文"异常处理"章节的素材。**

## 四、类设计（论文第 5 章的类图直接照此画）

| 类/接口 | 职责 |
|---|---|
| `FeatureService` | 构建与缓存商品特征向量、触发重算 |
| `UserProfileService` | 由行为日志聚合用户画像，处理时间衰减 |
| `RecommendService` | 推荐总编排：召回 → 过滤 → 打分 → 排序 → 理由 → 留痕 |
| `RecallStrategy`（接口） | 召回策略：`ContentRecall`、`SeasonRecall`、`HotRecall`、`ItemCfRecall`、`InventoryRecall`、`FallbackRecall` |
| `ScoreFactor`（接口） | 打分因素：`ContentFactor`、`SeasonFactor`、`CfFactor`、`PopularityFactor`、`PriceFactor`、`QualityFactor`、`InventoryFactor` |
| `SimilarityUtil` | 余弦相似度、Jaccard、min-max 归一化（静态工具类） |
| `Diversifier` | 多样性打散（贪心 MMR） |
| `ReasonGenerator` | 推荐理由模板生成 |
| `RecommendConfigService` | 读取权重方案与规则（置顶/屏蔽/保量），支持版本化 |
| `RecommendEvaluator` | 离线评估主类（带 `main` 方法），输出指标 CSV |

这种"策略接口 + 多实现"的写法有个额外好处：写论文时**每个召回通道、每个打分因素都能单独成节**，篇幅自然就有了，而且答辩时可以说"新增一个因素只需实现一个接口"。

## 五、关键代码骨架（每段都不超过 30 行，符合论文限制）

### 5.1 余弦相似度（含防除零）

```java
public static double cosine(double[] a, double[] b) {
    if (a == null || b == null || a.length != b.length) return 0D;
    double dot = 0D, na = 0D, nb = 0D;
    for (int k = 0; k < a.length; k++) {
        dot += a[k] * b[k];
        na  += a[k] * a[k];
        nb  += b[k] * b[k];
    }
    if (na == 0D || nb == 0D) return 0D;          // 防除零：新用户/新商品
    return dot / (Math.sqrt(na) * Math.sqrt(nb));
}
```

### 5.2 多因素加权打分（缺失维度自动重新归一化）

```java
public double score(UserProfile u, ItemFeature i, RecommendConfig cfg) {
    double sum = 0D, weightSum = 0D;
    for (ScoreFactor f : factors) {                 // 7 个因素，Spring 注入
        Double v = f.value(u, i);                   // 数据缺失返回 null
        double w = f.weight(cfg);                   // 权重来自可配置方案
        if (v == null || w <= 0D) continue;         // 缺失即跳过，不当作 0 分
        sum += w * clamp01(v);
        weightSum += w;
    }
    double base = weightSum == 0D ? 0D : sum / weightSum;
    return base - penalty(u, i);                    // 复购/不感兴趣/差评惩罚
}
```

### 5.3 ItemCF 相似度

```java
// 1) 从订单/加购构建 item -> Set<userId>
// 2) 共现计数：同一订单或同一会话中出现过，co(i,j) += 1
// 3) 相似度公式：
public double itemSim(long i, long j) {
    double co = coOccurrence.getOrDefault(key(i, j), 0D);
    if (co == 0D) return 0D;
    double denom = Math.sqrt(userSet(i).size() * (double) userSet(j).size());
    return denom == 0D ? 0D : co / denom;           // 余弦型归一化
}
// 4) 打分：cf(u,i) = Σ_{j∈用户历史商品} itemSim(i, j)，再做 min-max 归一化
```

### 5.4 推荐理由生成

```java
public String generate(List<FactorScore> factors) {
    return factors.stream()
        .filter(f -> f.contribution() > 0)
        .sorted(Comparator.comparingDouble(FactorScore::contribution).reversed())
        .limit(2)                                   // 取贡献最大的两个因素
        .map(FactorScore::text)
        .collect(Collectors.joining("；"));
}
```

### 5.5 离线评估主类（替代 Python 脚本）

```java
public static void main(String[] args) {
    // 1) 按时间切分：前 80% 行为建画像，后 20% 行为作为测试集
    // 2) 对每个测试用户生成 Top-10 推荐
    // 3) 命中测试期实际下单/加购的商品记为正样本
    // 4) 计算 Precision@K、Recall@K、NDCG@K、商品覆盖率、长尾曝光占比
    // 5) 依次跑 6 个方案：随机 / 热销 / 纯内容 / ItemCF / 多因素加权 / 加权+CF融合
    List<EvalResult> results = evaluator.runAllSchemes();
    CsvWriter.write("recommend_eval_result.csv", results);   // 用 Excel 画柱状图
}
```

**指标计算口径要在论文里写清楚**：Precision@K = 命中的推荐商品数 / K；覆盖率 = 被推荐过的商品数 / 在售商品总数；长尾曝光占比 = 销量排名后 50% 的商品在推荐结果中的占比。这三个指标直接对应"相关性"和"覆盖率"两项任务书要求。

## 六、人工调整功能怎么实现

| 调整入口 | 实现方式 |
|---|---|
| 运营调权重 | 后台权重方案编辑页（滑块）→ 存入 `recommend_config.weights_json` → 发布为新版本 → 缓存 key 变化，立即生效，可回滚 |
| 置顶/屏蔽/保量 | `recommend_config.rules_json` 记录规则，排序后应用（置顶插队、屏蔽剔除、保量预留坑位） |
| 用户改偏好 | 偏好设置页写入 `member_preference`，下一次请求生效 |
| 用户点"不感兴趣" | 写入 `recommend_feedback`，立刻加入惩罚项 |

每次调整记录操作人、调整前后权重、时间，写入操作日志——**这条链路既是功能，也是论文"人工调整"要求的证据**。

## 七、开发顺序建议（插进 13 天冲刺的位置）

| 时机 | 做什么 |
|---|---|
| 第 1–2 天 | 建好 `user_behavior_log`、`product_feature`、`member_preference`、`recommend_config`、`recommend_trace` 五张表，并写好埋点接口 |
| 第 3–9 天 | 商品、购物车、订单等模块**边开发边埋点**，数据自然积累 |
| 第 10 天 | 实现特征构建 + 5 通道召回 + 加权打分 + 理由生成（约 1 天可完成核心链路） |
| 第 11 天 | 推荐接口接入首页，后台权重配置页 |
| 第 12–13 天 | 造模拟数据、跑离线评估脚本、生成指标 CSV |
| 10 月之后 | 补 ItemCF、多样性打散、A/B 分桶、更多因素与对比实验 |

**别把推荐放到最后做。** 推荐的效果依赖行为数据积累，越早埋点，10 月做实验时数据越像真的。
