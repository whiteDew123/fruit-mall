## 1. 项目定位与范围

### 1.1 一句话定位

一个**平台自营**的水果电商系统：消费者端负责浏览、个性化选购、下单、支付、查看履约与评价；商家运营端负责商品建档、特色属性维护、库存与批次管理、订单处理、经营分析、推荐规则调整；履约与售后人员负责分拣配送状态推进与售后处理。核心智能化能力是**以多因素加权内容匹配为主、协同过滤为辅的水果推荐服务**，能说明"为什么推荐它"，并允许人工调整。

### 1.2 关键假设【待定】

| 编号 | 决策点 | 选项 | 我的建议 |
|---|---|---|---|
| D1 | 经营模式 | 单商家自营 / 多商家入驻 | **单商家自营（已确认，2026-09-23）**。多商家会引入店铺、入驻审核、佣金结算、跨店订单拆分，工作量翻倍且与选题描述不符 |
| D2 | 消费者端形态 | 响应式 H5 / 微信小程序 / 桌面 Web | **响应式 H5（移动优先）**。演示方便、一套代码；若导师明确要小程序，用 uni-app 同时出 H5+小程序 |
| D3 | 支付 | 真实支付 / 模拟支付网关 | **模拟支付网关**（任务书明确"模拟支付"）。但要把支付状态机做完整：待支付、支付中、成功、失败、关闭、退款，含幂等与超时 |
| D4 | 履约 | 对接真实物流 / 内部角色流转 | **内部角色流转**，但要产出履约记录与时间节点，形成可追溯链路 |
| D5 | 后端技术栈 | Java(Spring Boot) / Python(Django、Flask) / Node | **Java 17 + Spring Boot 3.5 + MyBatis-Plus，自建精简骨架**（已定，2026-09-24）。不使用第三方后台框架，代码全部可控可解释；推荐算法同样用 Java 实现，不引入 Python 服务 |
| D6 | 推荐算法 | 多因素加权内容匹配 / 协同过滤 / 两者结合 | **以多因素加权内容匹配为主实现，ItemCF 作为召回分支与对比实验基线**（理由见第 7 节）。确认**使用 Java 实现**，不引入 Python，详见 `04-推荐算法Java实现方案.md` |

### 1.3 明确不做（防范围膨胀）

优惠券、秒杀、拼团、积分体系、多语言、多币种、发票、客服 IM、真实支付通道、真实地图配送调度、多级分销、直播带货。

这些一律列为"后续扩展"，写进论文第 7 章展望即可。**每加一个功能，都会直接挤占推荐算法和测试的时间。**

## 2. 角色与权限设计

### 2.1 角色职责矩阵

| 角色 | 使用者 | 主要职责 | 关键权限 | 数据范围 |
|---|---|---|---|---|
| 游客 | 未登录用户 | 浏览、检索、看推荐 | 商品浏览、分类检索、查看评价 | 仅上架商品 |
| 注册会员 | 消费者 | 选购、下单、支付、评价、售后申请 | 购物车、订单、支付、地址、偏好设置、不感兴趣反馈 | 仅本人数据 |
| 商家运营人员 | 商家 | 商品建档、上下架、库存批次、订单处理、经营分析、推荐权重调整 | 商品/库存/订单/统计/推荐配置 | 全店经营数据（不含用户隐私字段） |
| 履约与售后人员 | 仓库/配送/售后 | 分拣、配送状态推进、异常登记、售后审核与处理 | 履约单、售后单、退款确认 | 履约与售后相关单据 |
| 系统管理员 | 平台 | 账号、角色、权限、日志、字典、参数 | 系统管理全部 | 全部（操作留痕） |

### 2.2 权限模型

采用 **RBAC（用户–角色–权限–菜单）**：后端接口用注解做功能级鉴权，Service 层做数据级校验（会员只能操作自己的购物车/订单/地址；运营不能看到用户手机号明文）。

要在论文里体现的两点：

- **功能级 + 数据级双重校验**：不能只靠前端隐藏按钮。越权访问（用 A 的 token 访问 B 的订单）必须返回 403 而不是 200。
- **最小必要授权**：用户手机号、收货地址在列表页脱敏（138****8888），只有必要场景（下单、履约）才展示完整信息，且展示行为写入操作日志。

## 3. 业务流程闭环与状态机（论文重点，答辩必问）

### 3.1 主业务流程

```
商品建档 ──▶ 浏览/检索/推荐 ──▶ 加入购物车 ──▶ 订单确认（校验价格/库存/地址）
   │                                                        │
   │                                            库存预占（锁定）
   ▼                                                        ▼
库存批次入库 ──▶ 库存流水                              模拟支付（幂等/超时/失败）
                                                            │
                     ┌──────────────────────────────────────┤
                     ▼                                      ▼
             支付成功 → 履约单创建                    支付失败/超时 → 关单 + 释放库存
                     │
        待分拣 → 分拣完成 → 待配送 → 配送中 → 已送达 → 已签收
                     │
                     ▼
              订单完成 ──▶ 售后申请（退货退款/仅退款）/ 评价 ──▶ 经营分析
```

### 3.2 四个状态机

**这是最能体现"数据库一致性校验"的内容，建议在第 4 章用状态图 + 第 6 章用测试用例双重呈现。**

**（1）订单状态机**

| 当前状态 | 允许迁移到 | 触发者 | 前置校验 |
|---|---|---|---|
| 待支付 PENDING_PAY | 已支付 PAID / 已取消 CANCELLED | 用户 / 系统超时 | 支付成功回调 / 超过 30 分钟 |
| 已支付 PAID | 备货中 PICKING / 退款中 REFUNDING | 履约人员 / 用户申请 | 履约单创建成功 |
| 备货中 PICKING | 配送中 DELIVERING | 履约人员 | 分拣完成且库存实扣成功 |
| 配送中 DELIVERING | 已签收 COMPLETED | 履约人员 / 用户确认 | 配送员送达 |
| 已签收 COMPLETED | （终态，可发起售后） | — | — |
| 已取消 CANCELLED | （终态） | — | — |

非法迁移必须被拒绝并记录：例如"待支付 → 配送中"、"已取消 → 已支付"、"已签收 → 待支付"。

**（2）支付状态机**

`INIT → PAYING → SUCCESS / FAILED → CLOSED`，退款走 `SUCCESS → REFUNDING → REFUNDED`。

关键点：支付流水号唯一索引保证回调幂等；支付金额必须与订单金额一致；已关闭订单不能支付；同一个订单不能被重复支付（第二次回调直接返回成功但不产生新流水）。

**（3）履约状态机**

`待分拣 → 分拣完成 → 待配送 → 配送中 → 已送达 → 已签收`，另有 `异常（破损/缺货/拒收/改期）` 分支。每个节点写入履约记录表（操作人、时间、备注、异常原因），形成时间轴，既供用户查看，也供论文第 4 章画顺序图。

**（4）售后状态机**

`待审核 → 已同意/已驳回 → 退货中（退货退款场景）→ 退款中 → 已完成`，也支持 `已取消`。

关键一致性：可售后数量 ≤ 订单项数量 − 已售后数量；只有已支付之后的订单才可发起售后；退货回补的库存进入"退货暂存批次"而不是直接回到可售库存——**生鲜退货不可二次销售，这个细节会让答辩老师印象深刻**。

### 3.3 一致性规则清单（第 6 章的测试对象）

| 编号 | 场景 | 规则 | 校验位置 | 失败响应 |
|---|---|---|---|---|
| R-01 | 商品上架 | 至少 1 张图、价格>0、必填特色属性齐全、可售库存>0 | Service + 数据库约束 | 400 并列出缺失项 |
| R-02 | 加入购物车 | 商品处于上架状态、库存>0、数量不超过限购 | Service | 400 "商品已下架/库存不足" |
| R-03 | 提交订单 | 重新校验价格与库存（不能信任前端），锁定库存，生成商品快照 | Service + 事务 | 409 "库存不足，请重新选择" |
| R-04 | 模拟支付 | 幂等（支付流水号唯一）、金额一致、订单必须待支付 | Service + 唯一索引 | 重复回调返回成功且不重复扣款 |
| R-05 | 超时关单 | 30 分钟未支付自动取消并释放预占库存 | 定时任务 | 用户再次支付被拒绝 |
| R-06 | 订单取消 | 仅待支付/已支付未备货可取消；已支付取消走退款流程 | 状态机守卫 | 409 "当前状态不可取消" |
| R-07 | 履约推进 | 必须按状态机顺序推进，不得跳级 | 状态机守卫 | 409 "非法状态流转" |
| R-08 | 售后申请 | 可售后数量 ≤ 订单项数量 − 已售后数量 | Service | 400 "超出可售后数量" |
| R-09 | 退货回补 | 回补至"退货暂存"批次，不进入可售库存 | Service | 记录库存流水类型=退货回补 |
| R-10 | 评价 | 仅已完成订单可评，一个订单项一次评价 | Service + 唯一索引 | 409 "已评价" |
| R-11 | 并发扣减 | 禁止负库存，条件更新或乐观锁 | SQL + 事务 | 库存不足则整单回滚 |
| R-12 | 商品下架 | 已加购项不强制清除，但下单时拦截 | Service | 409 并标记失效项 |

## 6. 领域模型与数据库设计

### 6.1 核心实体关系（用于第 4 章 ER 图）

```
会员 1─N 收货地址
会员 1─N 购物车项 N─1 SKU
会员 1─N 订单 1─N 订单项 N─1 SKU
订单 1─1 支付记录
订单 1─N 履约记录
订单 1─N 售后单 1─N 售后项
订单项 1─1 评价
分类 1─N 商品(SPU) 1─N SKU
SKU 1─N 库存批次 1─N 库存流水
会员 1─N 行为日志 ; 会员 1─1 偏好画像
推荐权重方案 1─N 推荐结果留痕 ; 会员 1─N 推荐反馈
角色 N─M 权限 ; 用户 N─M 角色
```

设计上的两个刻意选择，写论文时要说明：

- **SPU/SKU 两级**：芒果（SPU）下有 5 斤装/10 斤装/礼盒装（SKU），价格与库存挂在 SKU 上。这是电商标准做法，也方便推荐按 SKU 还是按 SPU 展示的讨论。
- **批次（batch）维度库存**：水果保质期短，必须按入库批次管理，才能实现临期预警、先进先出（FIFO）扣减和损耗统计。这是与普通商城最大的结构差异之一。

### 6.4 防超卖方案（必须能讲清楚）

推荐方案：**Redis 预扣 + MySQL 条件更新兜底**，或（更简单、更稳的毕设方案）**纯 MySQL 条件更新**：

```sql
UPDATE product_sku
   SET stock = stock - #{qty}, locked_stock = locked_stock + #{qty}, version = version + 1
 WHERE id = #{skuId} AND status = 1 AND stock - locked_stock >= #{qty};
```

判断影响行数，等于 0 则抛出库存不足、整单回滚。支付成功时把 `locked_stock` 转为实扣并写 `inventory_transaction`；取消或超时则释放。**并发测试（如 200 线程抢 100 件）是论文第 6 章的必备用例，能直接证明"没有超卖"。**

## 7. 推荐算法设计（核心智能化功能）

### 7.1 为什么水果推荐不能照抄通用电商

水果有三个领域特性，直接决定算法设计：

1. **强时令性**：同一个用户 3 月爱草莓、7 月爱西瓜，偏好随时间漂移，静态画像会失效 → 必须引入时间/季节特征与时间衰减。
2. **强复购性**：水果是高频消耗品，用户上月买过苹果，本月大概率还会买 → **不能简单"已购即降权/过滤"**，要按"预计吃完周期"判断复购时机。
3. **易腐坏、非标**：库存有批次与保质期，滞销即损耗 → 推荐要**与库存协同**，给临期/滞销商品适度加权，把"推荐"变成"经营工具"。这一点是本课题相对普通商城系统最值得写的创新点。

### 7.2 特征构造

**商品特征（来自特色属性表，这是"多因素"的来源）**

| 特征组 | 具体字段 | 处理方式 |
|---|---|---|
| 品类 | 一级/二级分类 | one-hot 或品类偏好分布 |
| 口味 | 甜度分、酸度分、脆度分、多汁度、香气 | 归一化到 [0,1] |
| 产地 | 省份、经纬度带、是否地理标志 | 产地偏好 + 纬度带 |
| 规格 | 净重、单果重、果径、包装形式 | 数值归一 + 分档 |
| 价格 | 单价、单位价格（元/斤） | 分位数归一 |
| 时令 | 上市月份区间 | 当季=1，临近±1月=0.5，反季=0.1 |
| 品质 | 品级、糖度(Brix)、有机/绿色认证 | 加权评分 |
| 储存 | 常温/冷藏、保质期天数 | 影响履约与推荐时效 |
| 场景 | 家庭/送礼/办公/孕妇儿童 | 场景标签匹配 |

**用户特征**

- 显式：首次进入的 3–5 题口味问卷（可跳过）、忌口/过敏、价格区间偏好。
- 隐式：由行为日志聚合出的甜/酸/脆偏好均值、品类偏好分布、价格敏感度、购买频次与客单价、复购周期。

**情境特征**：当前月份/季节、天气（可选）、时段、节日（中秋/春节礼盒）、收货区域（配送时效）。

**行为权重与时间衰减**（隐式反馈强度）

| 行为 | 权重 |
|---|---|
| 浏览 VIEW | 1.0 |
| 搜索并点击 SEARCH_CLICK | 1.5 |
| 收藏 FAVORITE | 2.5 |
| 加购 CART | 3.0 |
| 下单 ORDER | 5.0 |
| 好评 REVIEW_GOOD | 4.0 |
| 差评 REVIEW_BAD | −4.0 |
| 退款/退货 REFUND | −5.0 |

时间衰减：`w' = w × exp(−λ × Δt)`，半衰期取 14 天（λ 由半衰期反推，论文里给出公式与取值理由）。

### 7.3 两阶段：召回 + 排序

**阶段一：召回（候选池 100–200）**

| 召回通道 | 说明 |
|---|---|
| R1 内容相似 | 用户偏好向量 × 商品特征向量余弦相似度 |
| R2 时令匹配 | 当季商品 ∩ 用户历史品类 |
| R3 热销榜 | 近 7 天销量/加购分品类 TOP |
| R4 协同过滤(ItemCF) | 基于"同一订单/同一会话共现"的商品相似 |
| R5 库存协同 | 临期/滞销商品（商家侧可开关） |
| R6 兜底 | 新品保量、全站热销 |

**阶段二：过滤**：下架、无库存、忌口/过敏命中、已购未到复购周期（降权而非删除）。

**阶段三：多因素加权排序**

```
score(u, i) = Σ_k ( w_k × f_k(u, i) ) / Σ_k w_k

默认权重（可在后台调整，属于"人工调整"的一部分）：
  f1 内容偏好匹配   w1 = 0.25
  f2 时令匹配       w2 = 0.15
  f3 协同过滤得分   w3 = 0.15
  f4 热度得分       w4 = 0.15
  f5 价格匹配度     w5 = 0.10
  f6 品质/新鲜度    w6 = 0.10
  f7 库存协同压力   w7 = 0.10
惩罚项：重复购买惩罚（按预计吃完周期）、"不感兴趣"惩罚、差评品类惩罚
```

实现要点（写进论文会显得专业）：各 `f_k` 先归一到 [0,1]；**当某个特征缺失时（如新用户无协同数据），该维度权重置 0 并对其余权重重新归一化**，避免把缺失值当成 0 分而误伤新用户与新品。

排序后做**多样性打散（MMR 思路）**：保证 Top-10 至少覆盖 3 个品类，避免"全是芒果"，也保证长尾商品有曝光机会。

### 7.4 推荐依据怎么展示

对每个推荐结果，取贡献最大的 1–2 个因素 + 命中的规则，套模板生成理由，并整体写入 `recommend_trace`。

示例：

- "当季推荐：海南贵妃芒正值 3–5 月上市期"
- "口味匹配：你近 90 天有 6 次购买糖度 ≥14 的芒果类商品"
- "同类复购：你上次购买苹果类商品是 24 天前，接近你的日常消耗周期"
- "热销：近 7 天本店销量第 2"
- "产地偏好：你常购南方热带水果"

`factors_json` 记录每个维度的原始分、权重、加权贡献，论文里可以直接用一张表展示 5 个用户的推荐依据明细，作为"可解释性"的证据。

### 7.5 人工调整（任务书明确要求）

两个层面都要做，答辩时可以分别演示：

**运营侧**：权重方案可视化编辑（滑块调权重）、保存为版本、设置生效范围（全局/品类/人群）、商品置顶/屏蔽/新品保量（如"新品固定占 3 个坑位"）、方案 A/B 切换。每次调整写操作日志与 `recommend_config` 版本，可回滚。

**用户侧**：偏好标签自助修改（更甜/不要太酸/价格上限）、对推荐结果点"不感兴趣"，反馈写回 `recommend_feedback` 并即时影响后续排序。

### 7.6 冷启动与边界条件（第 6 章测试用例）

| 场景 | 输入 | 期望行为 |
|---|---|---|
| 新用户零行为 | 无任何日志 | 返回"时令+热销"，理由标注"新客推荐"，不报错 |
| 新商品零销量 | 刚建档上架 | 靠内容相似度 + 新品保量进入推荐位 |
| 候选不足 | 全站在售只有 3 个商品 | 允许返回少于 N 条，兜底全量，不抛异常 |
| 忌口冲突 | 用户忌口芒果 | 结果中芒果数为 0，`trace` 中记录被过滤原因 |
| 库存为零 | 热销品缺货 | 不进入推荐结果，缓存需失效 |
| 商品下架 | 上架后下架 | 5 分钟内从推荐结果消失 |
| 推荐服务异常 | 超时/返回 500 | 3 秒内降级为规则排序，页面正常展示并静默记录告警 |
| 单品类极端偏好 | 用户只买苹果 | 多样性打散后 Top-10 品类数 ≥3 |
| 价格异常 | 全场单价 999 元 | 价格匹配不出现除零/NaN，排序稳定 |
| 同请求重复 | 同一用户连续两次 | 同一权重版本下排序稳定可复现 |

### 7.7 实验验证方案（"典型样例验证相关性、覆盖率和边界条件"）

**数据**：系统自造的模拟数据（建议 500 用户 × 200 商品 × 5 万条行为，用脚本生成并保证行为与用户口味画像一致）+ 公开数据集 Instacart Market Basket Analysis（生鲜购物篮数据，与本选题品类最贴合，用于协同过滤实验）。

|---|---|---|---|---|---|
| 随机推荐（基线） | | | | | |
| 热销榜（典型现状） | | | | | |
| 纯内容匹配 | | | | | |
| ItemCF 协同过滤 | | | | | |
| 多因素加权（本文） | | | | | |
| 多因素加权 + ItemCF 融合 | | | | | |

指标含义要在论文里写清楚：**相关性**用 Precision@K / NDCG@K（可辅以人工标注抽样）；**覆盖率**用"被推荐过的商品数 / 可推荐商品总数"；**长尾曝光占比**直接对应"减少滞销损耗"的经营价值。

### 8.2 技术选型

| 层次 | 选型 | 理由 |
|---|---|---|
| 后端框架 | Spring Boot 3.5 + Java 17（自建精简骨架） | 代码全部可控可解释，不为框架版本付出额外代价 |
| 持久层 | MyBatis-Plus + MySQL 8 | CRUD 与分页开箱可用，条件更新支撑库存扣减 |
| 认证授权 | 自研 JWT + RBAC（拦截器 + 自定义注解） | 满足"身份认证、角色权限"要求，且实现过程能完整讲清 |
| 缓存 | Redis | 商品缓存、推荐结果缓存、库存预占、限流 |
| 前端（消费者） | Vue 3 + Vite + Vant | 移动端组件完善，演示效果好 |
| 前端（后台） | Vue 3 + Vite + Element Plus + ECharts | 自建最简布局，不引入重型 admin 模板 |
| 可视化 | ECharts | 经营分析图表 |
| 推荐模块 | Java（业务模块内的独立包，无独立服务） | 与业务同工程、无跨语言部署成本；离线评估用带 main 方法的评估类输出 CSV |
| 接口文档 | Knife4j / SpringDoc OpenAPI | 自动生成，答辩加分 |
| 定时任务 | Spring Scheduler（可选 XXL-Job） | 超时关单、日统计、离线推荐预计算 |
| 测试 | JUnit 5 + MockMvc + Postman/Apifox + JMeter | 单元/接口/并发 |
| 部署 | 本机直跑为主，Docker Compose 可选 | 本机当前未安装 Docker；答辩以本机运行 + 操作录屏兜底 |

### 8.3 推荐服务落地方式（关键取舍）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 全 Java 内置实现 | 部署简单、无跨语言 | 特征工程与实验评估写起来费劲，算法部分难体现工作量 | 可作降级兜底实现 |
| B. Python 推荐微服务（推荐） | 算法实验、指标评估、图表生成方便；服务边界清晰；可写"降级与容错" | 多一个进程与语言 | **主方案 B**：Java 通过 HTTP 调用，超时降级到 A 的简化规则排序 |

这个"双实现 + 降级"的设计同时满足了任务书的"推荐算法"和"异常处理"，答辩时是一个明确的加分点。

### 8.4 工程规范（论文第 4 章可直接引用）

- 分层：Controller（参数校验）→ Service（业务与状态机）→ Mapper（数据）。
- 统一响应体 `{ code, message, data, traceId }`；统一分页 `{ pageNum, pageSize, total, list }`。
- 全局异常处理：业务异常、参数异常、鉴权异常、系统异常分类返回，不向前端泄漏堆栈。
- 操作日志：AOP + 注解，自动记录操作人、模块、方法、参数、结果、耗时、IP。
- 数据校验：DTO 层 `@Valid` + 业务层二次校验（库存、状态、归属、金额）。
- 敏感数据：手机号/地址脱敏，日志打码，导出接口单独鉴权。

## 9. 接口设计要点

命名规范：业务接口分两个前缀，**不要混用**——消费者端 `/api/shop/{模块}/{资源}`，商家后台 `/api/admin/{模块}/{资源}`，登录注册在 `/api/auth/**`。动词用 HTTP 方法表达。响应统一为 `{ code, message, data }`，`code` 与 HTTP 状态码一致（200 成功 / 400 参数错误 / 401 未登录 / 403 无权限 / 404 不存在 / 409 状态冲突 / 500 系统异常）；分页请求 `pageNum`、`pageSize`，响应 `data` 为 `{ pageNum, pageSize, total, list }`。

关键接口清单（用于第 5 章"主要接口"与测试用例）：

| 模块 | 接口 | 说明 |
|---|---|---|
| 认证 | `POST /api/auth/register`、`POST /api/auth/login`、`POST /api/auth/logout` | 注册登录，返回 JWT |
| 商品（前台） | `GET /api/shop/product/list`、`GET /api/shop/product/{id}`、`GET /api/shop/category/tree` | 检索（含筛选/排序/分页）、详情、分类 |
| 购物车 | `POST /api/shop/cart/items`、`PUT /api/shop/cart/items/{id}`、`DELETE /api/shop/cart/items/{id}` | 加购、改量、删除 |
| 订单（前台） | `POST /api/shop/order/submit`、`GET /api/shop/order/list`、`POST /api/shop/order/{orderNo}/cancel` | 下单、列表、取消 |
| 支付 | `POST /api/shop/payment/pay`、`POST /api/shop/payment/callback` | 发起模拟支付、支付回调（幂等） |
| 履约 | `GET /api/shop/fulfillment/{orderNo}`、`POST /api/admin/fulfillment/{id}/advance` | 履约时间轴、状态推进 |
| 售后 | `POST /api/shop/aftersale/apply`、`POST /api/admin/aftersale/{id}/audit` | 申请、审核 |
| 评价 | `POST /api/shop/review/add`、`GET /api/shop/review/list/{productId}` | 评价与列表 |
| 推荐 | `GET /api/shop/recommend/items?scene=home&size=10`、`POST /api/shop/recommend/feedback` | 推荐结果（含理由）、不感兴趣反馈 |
| 推荐运营 | `GET /api/admin/recommend/config/list`、`PUT /api/admin/recommend/config`、`POST /api/admin/recommend/config/{id}/publish` | 权重方案管理与发布 |
| 商品与库存（后台） | `GET /api/admin/product/list`、`POST /api/admin/inventory/batch`、`GET /api/admin/inventory/flow` | 商品建档、批次入库、库存流水 |
| 统计 | `GET /api/admin/stat/overview`、`/sales-trend`、`/category-share`、`/slow-moving`、`/recommend-effect` | 经营分析与推荐效果 |

## 10. 测试方案

| 层次 | 内容 | 工具 |
|---|---|---|
| 单元测试 | 状态机迁移合法性、库存扣减逻辑、金额计算、推荐打分函数、权重归一化 | JUnit 5 |
| 接口测试 | 各模块正常流 + 参数校验 + 权限校验 | MockMvc / Postman 集合 |
| 集成测试 | 完整下单链路（加购→下单→支付→履约→签收→评价） | 自动化脚本 |
| 并发测试 | 同一 SKU 高并发下单（如 200 线程抢 100 件），验证无超卖、无负库存 | JMeter |
| 异常流程测试 | 重复支付回调、超时未支付后再支付、取消后支付、越权访问他人订单、库存不足、售后超量、推荐服务超时降级 | Postman + 日志核对 |
| 性能测试 | 商品检索与推荐接口 P95 响应时间 | JMeter |
| 数据一致性校验 | 订单金额汇总 = 订单项合计；库存流水累加 = 当前库存；订单状态与履约状态一致 | SQL 校验脚本 |

**建议做一个"一致性校验脚本"**（定时或手动执行），输出异常数据清单。它本身就是一个可以直接写进论文的工程亮点，答辩时能演示"系统自己发现数据不一致"。

## 14. 开题报告写作提纲（可直接照此填）

1. **选题背景与意义**：生鲜电商痛点（信息过载"千人一面"、易腐库存周转、供需错配）→ 引入个性化推荐的必要性。
2. **国内外研究现状**：推荐系统在电商的应用现状；协同过滤与内容推荐的优缺点；生鲜/时令品类推荐的已有研究（引用近五年文献，配合 fun-rec、RecBole 等来源）。
3. **研究目标与内容**：完整交易闭环 + 多因素加权推荐 + 可解释与可调整 + 实验验证。
4. **技术路线**：Spring Boot 3.5 + JDK 17 + MyBatis-Plus + MySQL 8 + Redis + Vue 3（自建精简骨架，不依赖第三方后台框架）；推荐算法用 Java 实现，采用两阶段结构（召回 + 多因素加权排序）。
5. **重点与难点**：并发库存一致性、状态机设计、推荐冷启动与可解释性、实验指标设计。
6. **进度安排**：按第 12 节表格。
7. **参考文献**：15 篇左右（近五年为主，含 2–3 篇推荐系统算法论文、2–3 篇生鲜电商研究、若干技术文献与开源项目电子文献）。
